# Framework Adapter Runbook

## Purpose and Ownership

Framework adapters translate between canonical `InvocationInput`/`InvocationOutput` and a
framework-owned runnable or graph. `NativeAgentInvoker` owns the built-in model/tool loop.
`LangChainRunnableAdapter` and `LangGraphAdapter` wrap public async framework objects through
explicit edge mappers.

Adapters do not own durable conversation history. PostgreSQL remains the source of truth, and the
runtime supplies prior messages before invoking an adapter.

## Prerequisites and Installation

```bash
uv add "agent-runtime-kit[adapters,postgres] @ git+https://github.com/Shengtao-Lin/agent-runtime-kit@v0.3.0"
```

The published v0.3.0 adapters include opt-in incremental streaming and require LangGraph >=1.2.11.
The historical v0.2.0 wrappers/native-message helpers retain their terminal fallback.

Before registration, decide:

- the stable public agent ID and semantic implementation version;
- the capability names returned through discovery;
- the exact framework input shape; and
- how the framework result becomes only the newly generated canonical messages and tool results.

## Adapter Selection

| Adapter | Use when | Streaming behavior |
| --- | --- | --- |
| `NativeAgentInvoker` | You want the kit's bounded provider/tool loop | True incremental streaming when the model client supports it |
| `LangChainRunnableAdapter` | You have an async object with `ainvoke()` | Non-streaming fallback unless a custom streaming invoker is implemented |
| `LangGraphAdapter` | You have a compiled async graph with `ainvoke()` | Non-streaming fallback unless a custom streaming invoker is implemented |

All three satisfy the same registry and runtime contracts.

## Integration Workflows

### LangChain runnable

```python
from agent_runtime.adapters import LangChainRunnableAdapter

adapter = LangChainRunnableAdapter(
    agent_id="support-langchain",
    version="1.0.0",
    runnable=runnable,
    input_mapper=to_runnable_input,
    output_mapper=from_runnable_output,
    capabilities={"support"},
)
agents.register(adapter)
```

### LangGraph graph

```python
from agent_runtime.adapters import LangGraphAdapter

adapter = LangGraphAdapter(
    agent_id="support-langgraph",
    version="1.0.0",
    graph=compiled_graph,
    state_input_mapper=to_graph_state,
    state_output_mapper=from_graph_state,
    capabilities={"support"},
)
agents.register(adapter)
```

Default input mapping remains canonical message dictionaries for compatibility. Default output
mapping also accepts native framework messages with the `adapters` extra installed. To supply
native messages explicitly, use:

```python
from agent_runtime.adapters.framework_messages import framework_input, framework_output

adapter = LangChainRunnableAdapter(
    agent_id="my-runnable",
    version="1",
    runnable=runnable,
    input_mapper=framework_input,
    output_mapper=framework_output,
)
```

The helpers support `SystemMessage`, `HumanMessage`, `AIMessage`, and `ToolMessage`, text blocks,
tool-call links/results, and token usage. UUID IDs are preserved; other framework IDs receive
deterministic UUIDs. Unsupported multimodal blocks, malformed tool calls, and partial chunks fail
closed and need an explicit mapper. Arbitrary framework response metadata/artifacts are not copied.
Supply custom mappers for custom state. These helpers import framework packages only when used;
ordinary core imports still need no framework dependencies.

## Mapping Contract

An input mapper receives the complete `InvocationInput`, including prior history, new messages,
runtime context, and metadata. An output mapper receives the framework result plus the original
input and must return `InvocationOutput`.

The output must contain only messages generated by this invocation. Returning input history again
causes duplicated durable messages. Do not configure persistent LangChain memory or a persistent
LangGraph checkpointer alongside the runtime's PostgreSQL history.

Built-in output mappers strip an exact input-history prefix (including message IDs). They cannot
infer which messages are old if a graph rewrites IDs/history; use an explicit mapper for that case.
The fictional example now executes the same model and shared tools through a real Runnable loop
and a compiled StateGraph model/tool cycle; neither framework owns a persistent checkpointer.

## Verification

```bash
uv run pytest tests/unit/test_adapters.py tests/unit/test_native.py -q
```

For each application adapter, add tests for:

- the minimum valid framework result;
- multiple generated messages;
- malformed or unexpected framework output;
- exception translation without sensitive error leakage;
- prior history appearing exactly once; and
- async cancellation reaching the wrapped object.

Discovery should report the configured ID, version, framework, and capability set. Invocation
through the Python runtime and optional HTTP service should produce the same canonical response
shape for every implementation.

## Streaming Expectations

The runtime accepts both `AgentInvoker` and `StreamingAgentInvoker`. Calling `runtime.stream()` on
a non-streaming adapter is supported, but it yields `started` followed by `completed` without text
deltas. Implement the optional streaming protocol only when the underlying framework provides a
stable incremental API and the adapter can still produce one terminal `InvocationOutput`.

### Incremental mode (v0.3.0 and later)

Pass `streaming=True` to either adapter to use its underlying `astream()` exactly once. Invocation
through `invoke()` still calls `ainvoke()`. Incremental delivery is opt-in; existing constructors
retain their terminal fallback and no framework import is added to core-only installations.

```python
adapter = LangChainRunnableAdapter(
    agent_id="chat",
    version="1",
    runnable=chat_runnable,
    input_mapper=framework_input,
    streaming=True,
)
graph_adapter = LangGraphAdapter(
    agent_id="graph",
    version="1",
    graph=compiled_graph,
    state_input_mapper=framework_input,
    streaming=True,
    stream_message_filter=lambda metadata: metadata.get("langgraph_node") == "answer",
)
```

The Runnable default supports one `AIMessageChunk` stream, accumulating text, tool arguments and
usage into a complete native message before output mapping. A single terminal state value is also
accepted, without fabricated deltas. Multiple message IDs, mixed snapshots/chunks, unsupported
content and invalid final tool calls need an explicit mapper and otherwise fail safely.
Assign a fresh message ID per generated message/invocation and keep that ID stable across its
chunks. Framework IDs are preserved/deterministically mapped; a constant ID reused across runs
would collide with the global message primary key, just as a reused canonical UUID would.

The graph default requests legacy/v1 `messages` and `values` modes for compatibility with older
supported versions. Text chunks arrive incrementally; only the final state goes through the existing
state output mapper. It does not configure a checkpointer. Use `stream_message_filter` to select
the intended public node/model using framework metadata; without a filter every assistant chunk
in the selected graph stream is eligible, including intermediate model calls. Filtering deltas does
not redact persisted history or the final response; the output mapper owns that decision.

Tool results in the default translators are emitted from the normalized final output, just before
completion. Earlier tool completion events, custom state deltas, multi-message Runnable streams,
subgraphs or alternative event APIs require `stream_mapper`. This callable receives the raw async
iterator and `InvocationInput`, and yields canonical `AgentTextDelta`, `AgentToolResult`, and
exactly one `AgentCompleted`. A custom mapper enables streaming automatically and owns final
mapping; the graph still supplies the two configured v1 stream modes. Events after completion or
missing completion fail. Raw framework metadata/state is never forwarded to SSE or logs.

Runtime completion still follows output hooks and atomic persistence. A received text delta is
provisional; failed/cancelled streams commit no partial history. Close abandoned Python iterators;
the runtime closes the framework iterator even when cancellation occurs during queue backpressure.
Total invocation/cleanup budgets and idempotent terminal replay remain unchanged. The kit adds no
extra unbounded event queue; an underlying framework may have its own buffers and cancellation limits.

See [ADR 0010](../adr/0010-framework-incremental-streaming.md) and the independent wheel consumer.

## Troubleshooting

### Mapping fails after a framework upgrade

Capture the new input or output shape using synthetic data, update the explicit mapper, and pin the
framework version until the tests pass. Do not expose raw framework exceptions to public callers.

### Agent registration is rejected

Agent IDs are unique. Correct startup configuration or choose a distinct public ID; do not replace
registry entries dynamically while traffic is active.

### Conversation history appears twice

Remove framework-owned persistent memory or checkpointers and confirm the output mapper excludes
the messages present in `InvocationInput`.

### Streaming has no text deltas

This is expected with default adapter settings. On v0.3.0 or later, enable `streaming=True`
and confirm the underlying model actually emits chunks. A state-only Runnable produces no fake
text deltas. For custom framework events, supply and test an explicit `stream_mapper`.

### Cancellation leaves work running

Ensure the wrapped framework and any downstream tools propagate async cancellation. Bound external
calls independently so a cancelled runtime request does not leave unlimited background work.

## Security and Upgrade Notes

Mapper code is a trust boundary: it may see the full message history and metadata. Do not log raw
objects. Use public framework APIs, pin supported version ranges, and repeat contract tests before
upgrades. Framework-native persistence must not compete with runtime-owned PostgreSQL state.
