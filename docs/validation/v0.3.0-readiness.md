# v0.3.0 Candidate Readiness

This report records pre-publication acceptance following v0.2.0. v0.3.0 was subsequently published;
see [the actual release-wheel and application evidence](v0.3.0-publication.md).
Schema `0002` and canonical contract `v1` remain unchanged.

## Delivered scope

- Independent installed-wheel applications own real Runnable/StateGraph state, typed tools and
  host lifecycle; no example/private-module imports or persistent framework checkpointers.
- Representative clean lower/latest dependency profiles, bounded Python compatibility CI,
  real PostgreSQL pool/lock/backend probes and synthetic performance artifacts.
- Opt-in incremental framework translation, explicit stream mapping, graph node filtering,
  strict terminal output and deterministic close of the framework iterator.
- Native/Python and HTTP SSE acceptance for provisional deltas, final atomic persistence,
  terminal replay, failures and cancellation.
- Updated component/user runbooks, release notes and immutable v0.2.0 publication evidence.

## Findings reflected in the release

The old LangGraph 0.2.28 incremental cancellation path left an internal waiter pending. The
v0.3.0 adapter extra therefore requires graph >=1.2.11,<2 rather than retaining an unsupported
range. Core version resolution must satisfy the chosen graph as well. Consumer pytest treats
unraisable-exception warnings as failures.

Application messages need a unique ID per generated message and a stable ID across its chunks.
Reusing a constant framework ID across runs produces a deterministic canonical ID collision;
the synthetic consumers generate fresh IDs and verify repeatable execution on retained databases.

## Remaining boundaries

Default wrappers still use terminal fallback. Runnable defaults support one assistant message
stream or one terminal state. Graph defaults use v1 messages/values, with tool results from final
normalization. Earlier tool events and custom/multi-message shapes require a stream mapper.
Filtering text nodes does not redact final output/history. Framework buffers and non-cooperative
extensions remain host integration concerns.

No live-provider budget was used. A bounded slow-consumer baseline records Python peak allocation
while consuming 128 deltas per request beyond the runtime queue capacity. Provider canaries,
sustained-load memory characterization,
PyPI trusted publishing and deployment/tenant controls remain explicitly outside this acceptance.
See [operating boundaries](operating-boundaries.md) for the measured benchmark definition.
