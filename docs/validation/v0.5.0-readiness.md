# v0.5.0 Candidate Readiness

Date: 2026-11-05. This is candidate evidence, not publication or independent-application adoption.
The latest verified published wheel and Release Desk pin remain v0.4.2.

## Scope and compatibility

The candidate combines terminal stream/result contracts (PRs #36/#37), explicit policy acceptance
(#38), lazy adapter exports and boundary guards (#39), documentation/release guards (#40), and the
public-surface/compatibility work (#41). The release change adds actual v0.4.2 preserved-state
upgrade gates without removing any earlier paths. Package metadata targets 0.5.0; canonical `v1`,
schema `0002`, dependency ranges and existing import paths remain unchanged. Only the root package
version changes in `uv.lock`.

Stricter custom-extension validation is behaviorally significant even without signature changes.
The [upgrade guide](../upgrading-to-v0.5.0.md) covers EOF/cleanup, matching tool-call representations,
finite JSON payloads, provisional output and rollback limits. Workload/context-selection design
remains Stage D and is not bundled into this release.

The upgrade source is the actual GitHub v0.4.2 wheel, verified against SHA-256
`016af5bbc1568a495901945e687b267214d60effafc2db17f6f865259f46decf` before installation. The
source-version assertion runs before seeding. Only then does the harness install the non-editable
candidate, migrate twice, and verify exact response/history replay, feedback, standalone memory,
existing owner/lease fields and continued invocation. `upgrade-source.json`, `package-audit.json`
and the resolved dependency inventory retain provenance. A locally rebuilt v0.4.2 is not used.

Candidate distributions are under `build/v050-candidate/`. Reports under `build/` are local/CI
artifacts, not committed historical release assets. These tests use no live model credentials and
do not establish production capacity, arbitrary provider parity or exactly-once external effects.

## Remaining promotion gates

Before tagging, merge all relevant PRs after final-head checks and verify main CI plus release
rehearsal. Release gates must retain all historical upgrades, container shutdown and installed-wheel
checks. After publishing, inspect actual wheel/source/container assets, repeat independent install
and upgrade/provider acceptance against downloaded bytes, then update Release Desk's independent
manifest/lock/digest and verify published-version adoption. Record publication separately and only
then replace candidate/latest-release status claims.
